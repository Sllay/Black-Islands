# S01-RC0-R1 — Foundation Corrections / UI / Player / Building / AI / Persistence

## Purpose

Correction run before Season 2. This run is intentionally bounded to reduce Codex context/rate-limit burn. It does **not** replace the world generator or foliage/render stack; those are Run 2.

## Start state

- Start from current `main` after S01-P04.
- Preserve Godot 4.7.2, Godot MCP, Serena, Voxel Tools 1.7/v1.7x and existing validated gameplay.
- Work on a dedicated branch.
- Commit/push small checkpoints. Do not save all validation for the final turn.

## Product flow to establish

MainMenu
→ Worlds (max 5)
→ Player Profiles for selected world (max 5)
→ Gameplay

World and player identity are separate.

A player profile must be portable by design: one character may later enter multiple worlds/servers. A world may contain multiple player profiles. Do not couple character data to a single world identity.

## C01 — Main menu, settings and save-selection UX

### Main menu

Create a real main menu before SaveSelect:

- Play
- Multiplayer — visible but disabled
- Options
- Quit

Use production UI, safe-area aware, mobile landscape responsive.

### Options screen

Full screen, not popup. Tabs:

1. Audio — default open
2. Graphics
3. Other — visible but disabled

Persistent bottom actions on every enabled tab:

- Cancel
- Save & Exit

Changes are staged until Save & Exit. Do not mutate expensive runtime graphics repeatedly while dragging controls.

### Audio

Create and persist Godot audio buses:

- Music
- Audio (SFX/game audio)
- Voice (NPC vocal/grunt layer for now; future multiplayer voice is a different concern)

Each has integer slider 0–100, step 1. Convert user-linear volume to the engine dB domain correctly; 0 must mute rather than attempt impossible negative infinity as a normal dB value.

### Graphics model

Keep **renderer backend** separate from **quality preset**.

Renderer backends:

- Desktop: Forward+
- Mobile: Mobile renderer
- Compatibility: gl_compatibility fallback for weaker/unsupported devices

Quality presets:

- Low
- Medium
- High

Do not claim renderer backend can safely hot-switch in a running game. Persist the desired backend for next launch / platform export path. Runtime-safe quality settings may apply after Save & Exit.

Graphics tab:

- Low / Medium / High buttons in one horizontal exclusive group
- render-distance/ring control represented to the player as 2–10, default 6; internally document precisely what one step means and do **not** call it literal number of chunks if it actually represents a ring/radius
- Shadows toggle
- VSync toggle

Preset values must be data-driven in a `GraphicsProfile`/equivalent resource or catalog, not scattered conditionals.

### Worlds screen

Replace the old 4-slot shell with max 5 world slots.

Each populated slot is a horizontal card containing:

- compressed world preview captured from world-only render (no HUD/debug UI)
- world name
- difficulty
- accumulated real play time
- in-world day count
- Delete / Edit / Play, horizontal in that order

Empty slot:

- title `Vazio`
- text `Clique para criar o mundo`

Back returns to MainMenu.

Preview policy:

- fixed bounded resolution independent from device screen resolution; choose a practical 16:9 thumbnail size (for example 640×360) and document it
- no 4K/full-resolution save previews
- compression format/quality must be bounded and validated
- capture must not include HUD, QA, labels or debug overlays

### World create/edit screen

Create:

- World name LineEdit, generated `Mundo_###`
- seed LineEdit, generated if untouched
- click/focus should select all existing generated text for quick replacement
- difficulties Normal / Difficult / Extreme in horizontal exclusive group; Normal enabled and selected, other two visible but disabled for this chapter
- Back / Create

Creating metadata must not generate the full world immediately. It creates the world profile and moves directly to Player Profiles for that world. First actual entry owns generation/loading.

Editing an already-generated world:

- name may change
- seed is read-only/locked
- difficulty follows chapter policy

### Player Profiles screen

Max 5 player profiles associated with the current selection flow, but player identity/storage is architecturally portable and not owned by the world file.

Card:

- character appearance preview with current cosmetic clothing/tool/equipment visual representation when applicable
- character name
- level
- accumulated play time
- Delete / Edit / Play

Back returns to Worlds.

Empty player slot creates a new player.

### Player creation/customization

Build a real LPC customization shell from the catalog rather than hardcoded one-off fields. At minimum expose supported categories that exist in the pinned catalog, such as body type, skin, ears, face/eyes/hair and cosmetic clothing/accessories, filtered by catalog compatibility.

For Chapter 1 creation:

- male/female presentation available where catalog supports it
- pregnancy is **not** a creation option; it is future gameplay state
- generated/default character name can be replaced

After creation, Edit must **not** allow changing immutable identity/body traits that are intended to require in-game mechanics. Existing-character edit is primarily cosmetics/clothing/accessories. Hair/body-trait changes belong to future in-game systems unless explicitly enabled by design.

Do not expose raw upstream LPC paths as save identity.

## C02 — visual/player/camera/collision/building corrections

### LPC Sprite3D

Fix player presentation:

- camera-facing yaw only
- never lie flat / pitch with camera
- correct feet/root anchor
- visual may intersect neither ground nor nearby walls due to wrong transform origin
- collision is independent of sprite billboard

### Cameras

Establish two normal gameplay cameras/modes:

- angled 2.5D overview, less top-down than current
- third-person/shoulder mode available during ordinary gameplay

Building requires third-person precision mode, but third-person is not exclusive to building.

Transitions must preserve aim and controls.

### Collision layers

Refactor semantic layers/masks so interactivity is not the same as physical blocking. At minimum distinguish:

- terrain/world
- player
- mobs
- blocking structures
- interaction/query targets
- triggers

FarmPlots and loot bags must not become invisible physical blockers simply because they are interactable. Chests/structures may have separate physical and interaction representation.

### HUD cleanup

- remove permanent production tutorial text such as `Machado: árvores • Picareta: rochas...`; use contextual/tutorial messaging
- context button must reflect an actual available semantic action, not merely `TargetResult != NONE`
- mob HP/name Label3D presentation becomes debug-only or targeted/contextual, not permanently visible production UI

### Building scale/support

Correct placeholder physical scale before more content depends on it:

- one Foundation footprint becomes approximately 2×2 of the current 1 m cells (product target ~2 m × 2 m)
- foundation visibly thicker than ceiling
- wall/ceiling dimensions derive from the corrected module footprint
- pillar height remains coherent with wall module

Support truth:

- Foundation requires sufficient terrain support over its footprint, not just a center sample
- small local terrain loss may survive if support threshold remains
- substantial support loss collapses/removes the foundation
- dependent structure support graph updates locally
- chest or other placeable sitting on terrain/foundation must lose support when its support disappears
- destroyed chest preserves contents by atomically creating one loot bag/container; never delete contained items

Update material tier baseline to the agreed gameplay scale instead of current tiny placeholder HP. Preserve data-driven tiers. Current target order:

Thatch → Wood → Stone → Darkstone → Scrap → Iron

Use the project design baseline (Thatch starts at 5,000 HP) and document the full monotonic table chosen for this run rather than leaving 80/200-style prototype values.

## C03 — AI foundation, save split and migration foundation

### LimboAI

Install/integrate the compatible LimboAI release for Godot 4.7.2 following upstream docs. Use it for behavior/state orchestration rather than species-specific controller branches.

Do not make LimboAI own domain truth.

Architecture:

MobDefinition/MobDomain
→ LimboAI BT/HSM decides intent
→ MobLocomotion executes movement/navigation
→ MobActor is active presentation/physics adapter

Create reusable states/tasks such as idle, wander, flee, warn, chase, attack, sleep/deactivate as appropriate; species compose them from data.

### Mob locomotion

Do not leave `direction.normalized()` as the final navigation system. Add a locomotion/navigation seam capable of handling walls, structures, edited terrain and local avoidance. It may still use a minimal Chapter 1 implementation, but AI and locomotion must be decoupled.

### World/player persistence split

Refactor persistence so player state is not the owner of surface/world state.

PlayerProfile save owns only character-owned data such as:

- stable player ID
- name
- appearance/cosmetics
- stats/level/progression
- inventory/hotbar/equipment
- recipes/skills/unlocks when added
- character play time

World save owns world-owned data such as:

- seed/generation/profile metadata
- world clock/day
- terrain delta manifest/chunks
- structures
- farms
- containers/world drops
- props/regrowth
- mobs/NPC state
- future village/quest/world flags

A world session may maintain a small mapping of player ID → last world position/session state if required, but the portable player record must not be cryptographically/structurally locked to one world seed.

Existing S01 dev saves may be migrated or explicitly reset by a documented dev migration, but implement a versioned migrator path now:

schema N → migrator → N+1

Unknown future schema remains rejected safely.

### Save performance

Do not serialize/hash/rewrite the whole world merely because player inventory changed. Use dirty-domain tracking and bounded/coalesced commits. Preserve crash consistency with manifests/journals/temp+rename/checksums as appropriate.

## Validation strategy / token budget discipline

Do not spend one giant final turn running every historical gate repeatedly.

For each checkpoint:

1. targeted unit/smoke tests
2. one real MCP runtime proof
3. LSP diagnostics for changed scripts
4. commit + push immediately

At final gate:

- run only the minimum high-value regression set plus the new RC0-R1 validator
- reuse earlier P00–P04 evidence unless a touched subsystem requires its specific regression
- no extended performance benchmark in R1 except focused regression measurements for systems changed here
- mobile physical validation remains explicitly NOT VALIDATED if device export is unavailable

## Acceptance

R1 is complete only when the new menu→world→player→game flow works, settings persist, player/world saves are separated, visual/camera/collision/building issues above are corrected, LimboAI foundation is integrated, and existing core gameplay still works.

Do not begin RC0-R2/world-generation replacement in this run.
